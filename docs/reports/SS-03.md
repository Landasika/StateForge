# SS-03 完成报告：让 Fuzzer 自己拼多请求序列

## 提交

`0752a3c`

## 先说清楚它不是什么

它不是一个新的 Fuzzer。

Atheris 仍然是唯一的变异和执行引擎。这个模块只做一件事：在 Atheris 启动
之前，用一个小预算搜一次，看看能不能把几个单请求拼成能到目标的 C10 序列。
找到就写进语料，找不到就算了，不阻塞后面的 Fuzzing。

## 为什么不能直接给序列

任务里有一条硬要求：不能把 `登录 -> 访问个人页` 这种完整答案提前写好。

所以请求池只允许单请求：

```json
{"method": "POST", "path": "/authenticate", "form": {"passcode": "valid"}}
```

如果池子里出现：

```json
{"steps": [...]}
```

代码会直接报错，不接受完整序列。

## 搜索怎么做

### 候选

从每个单请求开始。之后每一步尝试：

- 追加一个单请求；
- 替换最后一步；
- 删除一步；
- 改请求里的参数值。

这些操作只看“请求结构”，不看业务名字。代码里没有硬编码
`/authenticate` 或 `/protected`。

### 打分

每个候选都真的执行一次，然后看 Trace 覆盖：

- 目标块覆盖：最高分；
- 写入块覆盖：加分，但只是进展；
- 离目标越近：加分；
- 序列越长：轻微扣分；
- 运行时 Session 条件确认：额外加分。

`guided=False` 是消融组：使用同一个请求池和同一套结构变异，但不按写入块
覆盖给候选排序。这样比较的是“定向”本身，不是“请求池不一样”。

### 预算和去重

- 固定 seed；
- `max_steps` 限制最长序列；
- `max_execs` 限制执行次数；
- 每个候选算一个规范化哈希，包含目标块、是否 guided、参数和步序；
- 重复序列不再执行。

### 隔离

每个候选开始前调用 `reset_hook()`，保证是干净客户端。

候选内部的多个请求共享同一个 Cookie Jar，这是 Session 能传递的前提。
候选之间不能共享。

## 怎么接进现有命令行

新增的开关默认关闭，不影响原来的 A–F/默认实验：

```bash
python -m stateforge.fuzzing.entry_driver ... \
  --session-guided \
  --session-target-block 'app.py::protected::173-173::block::1' \
  --session-request-pool pool.json \
  --session-max-steps 3 \
  --session-max-execs 60
```

启动时会先做一次搜索，把找到的 C10 序列写进语料，然后照常
`atheris.Setup` / `atheris.Fuzz()`。

## 怎么判定“成功”

分两种情况：

- 没有可靠的 Session 观测器：目标块到了也只能报 `PROXY_PROGRESS`，
  不能生成“已验证”的检查点；
- 有观测器：目标到了，并且 Session 条件组真的满足，才报 `VERIFIED`。

覆盖到写入块本身不算成功。写入块只说明“可能写了”，不说明“读的时候
值还在、还是对的”。

## 测试

```bash
python -m pytest stateforge/tests/fuzzing/test_session_guidance.py -q
```

结果：`9 passed`。

覆盖了：

- 从独立的单请求池里自己拼出两步序列；
- 拒绝包含 `steps` 的请求池；
- 没有观测器时只报 PROXY；
- 没有登录请求的池子到不了目标；
- 预算和去重生效；
- 找到的种子能在干净客户端重放；
- 第二次搜索不会受第一次影响；
- baseline 用同一个池子，结果可审计；
- 追加、替换、删除三种结构变异都能产生候选。

## 实际跑一次

在 `session_gate` 靶上，9 个单请求、60 次预算内，搜索用了 15 次执行找到：

```text
POST /authenticate {"passcode": "valid"}
GET  /protected
```

随后 Atheris 正常启动。`global_state.json` 里同时能看到目标块和
`Session.uid{client-0@session}`，值是 7。

## 这批判定不了什么

- 只证明在这个靶、这个请求池里能拼出来，不证明通用最优；
- 搜索执行数会计入总预算，所以不能简单说“比 baseline 快”；
- 目标块覆盖本身仍然需要 SS-04 的运行时条件判定来补足。
