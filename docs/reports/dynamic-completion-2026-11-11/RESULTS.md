# 动态回填：把 trace 接回 ICFG

日期：2026-11-11
范围：`stateforge/targets/apps20/` 下全部带 `harness.py` 的靶标。

## 要解决的问题

静态 ICFG 有一批调用点永远解析不了：接收者类型推断不出来（`obj.save()`、
`message_user()`），或者目标由运行时决定（`request.user`、插件注册表）。
仓库里补图的能力早就写好了——`learn_call_edges` 能从 trace 里学出
`(caller, line) -> callee`——但**全仓没有一处生产代码调用它**。
能力在，通路没接。

这次接的就是这一段。

## 断掉的三个点

| 环节 | 状态 |
| --- | --- |
| 采集 | 十几处都在建 `TraceSession`，`run_one` 每跑一个输入都有完整 trace |
| → 求解器 | `run_one` 返回的事件被直接丢掉，没人调 `learn_call_edges` |
| 入口 | 采集脚本 `trace_collect.py` 是临时文件，没入库 |

新增两个模块补上中间这段，按架构分层切开：

| 模块 | 层 | 职责 |
| --- | --- | --- |
| `stateforge/analysis/dynamic/collect.py` | L1 analysis | 纯逻辑：路径翻译、事件过滤、依赖根发现 |
| `stateforge/fuzzing/dynamic_collect.py` | L2.5 fuzzing | 驱动：装 `TraceSession`、跑 harness、喂 `learn_call_edges` |

拆开是必须的：`analysis` 位于 `runtime` 之下，不能导入 tracer。
`callgraph.py` 早就用 Protocol 回避了同一问题，这次沿用那条线——
上层负责"跑"，下层负责"算"。

`collect_target(label, ir, root)` 驱动靶标自己的 `smoke()`，采 trace，
喂给 `learn_call_edges`，返回可直接传给 `build_icfg(..., dynamic=...)` 的映射。

## 接入过程中发现的四个真问题

这四个都不是"采集器写得不对"，而是**静态图和动态 trace 对不上**的四种
具体形态。每一个都会让结果静默变成零，所以值得单独记。

### 1. harness 导入时改变工作目录

所有 harness 都会 `chdir` 进自己的应用目录（相对配置、fixture 路径要靠它）。
调用方用相对路径持有分析根目录时，`build_icfg(root)` 拿到的就是**另一个树**，
结果是 0 个函数——不是报错，是静默空图。

修法：入口先 `resolve()`，跑完恢复工作目录（`_restored_cwd`）。

### 2. venv 在应用目录内部

`TraceSession` 只按 root 前缀过滤。microblog 的 venv 在
`external/microblog/.venv`，整个依赖树都在 root 里面，于是 jinja2 的模板
编译被记了 **145 万条事件**，而它们对应的函数 IR 里根本没有。

修法：排除依赖根（按 `pyvenv.cfg` 发现 venv，和依赖切片用同一套判断——
两层必须对"什么算这个应用"有一致的定义）。事件从 145 万降到 7,587。

### 3. `pip install .` 装的是拷贝，图和 trace 各自看一份

fava / OctoPrint / Radicale / trac 的项目代码被**拷贝**进 site-packages，
而 IR 是从 `src/` 建的。trace 报 `site-packages/fava/core/number.py`，
IR 里叫 `src/fava/core/number.py`——路径对不上，四个靶标全部采到 0 条可用边。

修法：路径翻译（`path_translation`），按 site-packages 下的相对路径在
分析根里找回同名文件，**并用文件大小校验**。trac 装的拷贝和分析的源码
内容不同，这类翻译必须拒绝，否则会把行号改到图里没有的位置。

修好之后：fava 0 → 3,033 事件 / 21 条边，octoprint 0 → 75 万事件 / 808 条边，
radicale 0 → 26,953 / 149，trac 0 → 68 万 / 308。

### 4. 靶标自己跑不到业务代码

bakerydemo 采到 188 条事件、68 条能映射到 IR，但学到 **0** 条边。
原因不在采集：它的 harness 第一次渲染就抛
`TemplateDoesNotExist: base/standard_page.html`，业务代码没被执行到。
即使加上 venv 切片把函数数从 76 提到 15,807，仍然是 0 条边——
因为能映射到 IR 的调用都是 `search`/`columns` 这种没有出边的函数，
而真正的未解析点（`get_api_representation`、`get_image_model`）目标在
wagtail 里。

这是**两层分析互补**的直接证据：venv 切片（静态）给图补节点，
动态 trace 给图补边，缺哪一层都不行。bakerydemo 的 harness 环境本身
要修，不属于这次改动的范围，已记在遗留项里。

## 可达收敛率：1.6% 低估了

"关闭 1.6%" 不能直接读。分母里绝大部分未解析点位于**这次运行根本没进入
的函数**里——任何一次浅跑都动不了它们，把它们算在动态分析头上是不公平的。

有意义的分母是"调用者被执行到的那些点"，因为那才是运行有机会回答的部分。
`reach.py` 算这个：

| 靶标 | 未解析 | 其中可达 | 关闭 | 可达内收敛 | 进入的函数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| mezzanine | 2635 | 1304 | 201 | **15.4%** | 274/551 (50%) |
| zinnia | 1160 | 605 | 91 | **15.0%** | 173/371 (47%) |
| healthchecks | 3103 | 747 | 86 | **11.5%** | 293/760 (39%) |
| ctfd | 4641 | 1771 | 201 | **11.3%** | 309/841 (37%) |
| microblog | 567 | 351 | 36 | **10.3%** | 76/98 (78%) |
| wger | 5364 | 1226 | 36 | 2.9% | 547/1226 (45%) |

在运行真正走到的代码里，静态分析留下的未解析点被 trace 解决掉 **10–15%**。
这是单次浅跑的数字：多数靶标只发了 20–40 个请求，进入的函数不到一半。

wger 只有 2.9% 说明这个数字不是靶标无关的常数：它进入函数比例不低
（45%），但学到的边少——`ReactView` 的入口语义让静态图里的调用点
和运行时帧对不齐，这是已记录的另一类问题，不是采集器的事。

覆盖和收敛是乘法关系：`613/3995 = 15.3%` 的块覆盖是之前实验就记下的
天花板。**动态回填收益随覆盖率增长，不是一次性常数**——这正是它该接进
fuzzing 主循环的理由。

## 明确的边界

* 动态边只增不减。不回退、不删除任何静态边。
* 动态边不计入覆盖率指标，只累积。
* 冲突的调用点（同一点学到多个目标）由 `learn_call_edges` 丢弃，
  这类歧义不做猜测。

## 遗留

1. **没接进 fuzzing 主循环**：`run_one` 仍然丢弃事件。接上它，覆盖率会
   随 fuzz 时长持续累积，这才是收益最大的地方。
2. **缓存没自动加载**：`DynamicEdgeCache` 支持磁盘持久化和 source hash
   失效，但 `build_icfg` 还不会自动读它，目前要显式传 `dynamic=`。
3. **bakerydemo harness** 模板缺失，业务代码跑不到。
4. **realworld** 靶标没有 `harness.py`，无法动态采集。
