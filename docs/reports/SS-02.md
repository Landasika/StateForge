## 这一批解决什么问题

SS-01 找到了所有 Session 读写，但还回答不了：

> 目标基本块需要 `uid`，那 `uid` 可能是谁写的？

这一批做两件事：

1. 建一个按 key 查的索引；
2. 从目标块出发，沿控制流找条件，再反查候选写入块。

## 索引

`SessionAccessIndex` 把访问分成读、写、删除、清空几类，按
`backend + key` 分组。

查询时是“一个读取点查一次”，不是把所有写和所有读做成大表。这样代码量
和行为都更可控，也不会在大型程序里先炸一次笛卡尔积。

几个规则：

- 常量 key 和常量 key 相同，才是 `MUST_OVERLAP`；
- 动态 key、未知 key、`clear()` 只能算 `MAY_OVERLAP`；
- 两个不同的常量 key 是 `DISJOINT`；
- 静态阶段不知道客户端，所以所有候选都带一条约束：
  `writer.?client == reader.?client`；
- backend 也进索引键，Flask Cookie Session 不会被和别的 Session 后端
  混在一起。

## 目标查询

`query_session_frontier()` 的做法不复杂：

1. 在目标函数里，从入口到目标块枚举路径；
2. 每条路径上，遇到 `if` 就看它的条件和走了哪条边；
3. 把和 Session 有关的条件收集起来；
4. 每个条件去索引里找候选写入块；
5. 把路径条件、读取点、候选写入块、未解析项一起返回。

几个例子：

```python
uid = session.get("uid")
if uid is None:
    return "deny"
return "target"
```

目标在提前返回之后，所以需要的是 `uid EXISTS`，不是 `uid is None`。

```python
if uid == 7:
    return "target"
```

需要的是 `uid == 7`。

```python
if uid:
    return "target"
```

需要的是 `TRUTHY`。`TRUTHY` 不等于 `EXISTS`：值为 `0`、`False`、空字符串
时 key 可能仍然存在，但条件不成立。

```python
if "uid" in session:
    return "target"
```

需要的是 `EXISTS`。

几条重要边界：

- 两条互斥分支各自有一组条件，不会被强行 AND 成一组；
- 无法解析的守卫会放进 `unresolved`，结果标 `partial=True`，不猜；
- 分支里给同一个变量赋了不同 Session key 时，变量会降级成
  `KEY_UNKNOWN`，不会偷偷取第一个；
- `clear()` 会作为“能破坏所有 key”的候选出现。它可能满足“key 不存在”，
  但不能满足 `uid == 7`；
- 只写 `other` 的块不会匹配 `uid`。

## 测试

```bash
python -m pytest \
  stateforge/tests/state/test_session_index.py \
  stateforge/tests/state/test_session_goal_query.py -q
```

结果：`14 passed`。

覆盖了：

- `/protected` 能反查到 `authenticate` 的 `uid=7` 写入块；
- `logout` 的 `pop(uid)` 和 `clear()` 会作为破坏候选出现；
- 只写 `other` 不会被当成 `uid` 的写入；
- 动态 key 是 MAY，不是 MUST；
- 目标是“uid 不存在”时，DELETE/CLEAR 排在 SET 前面；
- 两条互斥路径保留成两组条件；
- 分支歧义别名降级为 `KEY_UNKNOWN`；
- 非 Session 守卫会标 unresolved/partial；
- 同一输入查询两次结果一致；
- 返回结果里所有依赖都是 `STATIC_MAY`，没有假装 verified。

## 这批判定不了什么

- 不能证明运行时是同一个客户端，只是把“同客户端”作为约束带上；
- 不能证明候选写入真的执行过；
- 不能证明目标已经到达；
- `partial=True` 不是失败，它表示还有没证明的部分。
