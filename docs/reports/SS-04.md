# SS-04 完成报告：运行时确认、重放和隔离

## 提交

## 这一批解决什么问题

SS-03 能找到目标块，但“目标块被覆盖”仍然可能骗人：

- 守卫走了真分支，不代表 Session 值就是目标要的值；
- HTTP 200 不代表目标到了；
- 命中写入语句不代表写入成功。

这一批做运行时确认，并且只在确认成功时保存检查点。

## 运行时观测

观测点放在响应之后、客户端 Cookie Jar 已经更新之后。

做法是从当前客户端读出签名 Cookie，用应用自己的 Session 接口解码。
它不会：

- 调用路由；
- 发新请求；
- 修改 Cookie；
- 用 HTTP 状态码猜 Session。

结果分三种：

| 结果 | 含义 |
|---|---|
| `VERIFIED_TRUE` | 条件确认成立 |
| `VERIFIED_FALSE` | 条件确认不成立 |
| `UNKNOWN` | 无法确认 |

`invalid` 和 `unknown` 只能保持 `UNKNOWN`。不能把“Cookie 坏了”当成
“没有 Session”，也不能把“没观测到”当成 `False`。

每个观测都带：

- `client_id`：哪个客户端；
- 观察点：响应后、前缀重放后等；
- key 和裸值；
- 值类型：`NUMBER`、`STRING`、`BOOLEAN`、`NULL`、`MISSING`、`UNKNOWN`。

`NULL` 和 `MISSING` 是两回事：

- `{"uid": None}` 是 key 存在，值为空；
- `{}` 是 key 不存在；
- 坏 Cookie 是 `UNKNOWN`，不是“key 不存在”。

## 条件判定

支持：

- `EXISTS` / `NOT_EXISTS`；
- `TRUTHY` / `FALSY`；
- `EQ` / `NE`；
- `IN` / `NOT_IN`。

条件组是 AND：组里所有条件都为真，才算 `VERIFIED_TRUE`。

如果目标是“uid 不存在”，那么空 Session 可以确认；如果目标是
`uid == 7`，空 Session 会确认失败，而不是 `UNKNOWN`。

## 检查点

检查点只从同时满足两件事的结果创建：

1. 目标块真的到了；
2. Session 条件组真的验证通过。

检查点保存：

- 已验证的请求前缀；
- 条件组；
- 观测到的 Session 值；
- 写入块；
- 对应的运行时证据。

它不是把所有请求都存下来。只存已验证前缀，后面可以接新的后缀。

## 重放

重放流程：

1. 先 reset，保证是干净客户端；
2. 执行验证过的前缀；
3. 重新读 Cookie，重新判定条件；
4. 如果给了后缀，再执行后缀；
5. 后缀单独执行时，不能借用前缀的会话。

判定结果：

- 目标到了，条件也成立：`REPLAY_VERIFIED`；
- 目标到了，条件不成立：`TARGET_ONLY`，不是成功；
- 目标没到，观测也不可信：`REPLAY_UNKNOWN` 或 `REPLAY_FAILED`。

这样不会出现“重放跑完了，所以一定成功”的假阳性。

覆盖了：

- 缺前缀时目标不到，不假成功；

## 这批判定不了什么

- 只适用于 Flask 默认签名 Cookie Session；
- 服务端 Session、JWT、其他框架需要新的 observer；
- `absent` 只在当前客户端、当前观察点内可信，不能跨客户端推断；
- 检查点只适合已验证前缀，不能拿它去证明别的目标。
