## SS-05A：搜索器不该知道“valid”

### 问题

`SessionGuidedSearch._collect_values()` 以前会在请求池的值后面再加：

```python
("valid", "wrong", "admin", "7", "0", "")
```

这等于把当前微靶的密码直接写进通用搜索器。用这种搜索器证明“状态依赖
引导有效”没有说服力。

### 改法

- 删掉 `valid / wrong / admin / "7"` 这类业务值。
- 只保留从合法单请求池采集的值，以及明确标记的类型边界：
  `None / True / False / 0 / 1 / ""`。
- 每个候选值带来源：
  - `single-request-pool`
  - `generic-boundary`
- 每个候选序列记录它用到的参数来源，写进 `GuidedAttempt.to_dict()`。

请求池仍然可以包含一个合法的单请求，这是真实测试的前提；但完整成功序列
仍然禁止，`steps` 会被拒绝。

### 反例

新增测试：

- 口令改成 `gate-9f3a`，路由改成 `/p1`、`/p2`，搜索仍能拼出两步；
- 池子里只有错误口令，搜索不能靠内建 `valid` 意外成功；
- 把 Session key 改成 `token`、目标函数改成 `secret_zone`，索引仍能找到；
- 候选值里没有 `valid`、`admin`、字符串 `"7"`；
- 候选序列能追溯参数来源。

结果：`30 passed`（`test_session_guidance.py` 12 + `test_session_goal_query.py`
4 + `session_gate` 14）。

## SS-05B：一把尺子量 Session 条件

### 问题

以前有三套近似判定：

- `session_guided._condition_matches()`
- `session_guided.group_satisfied()`
- `session_observation.evaluate_session_conditions()`

它们对空条件组、缺 key、`None` 的处理不一致。最危险的是：

- 空条件组可能被当成 True；
- 缺 key 的 `EQ None` 可能因为 Python `None == None` 变成 True；
- invalid Cookie 可能被包装成 `{}`，看起来像空 Session。

### 改法

- `evaluate_session_conditions()` 成为唯一权威入口。
- `group_satisfied()` 保留为兼容包装，内部转调权威入口。
- `SessionSnapshotView` 增加 `source`，保留
  `status / client_id / observation_point / observed_at`。
- 搜索器不再把 view 转成裸 dict；`SessionGuidedSearch._probe()` 返回 view。
- `_module_session_probe()` 返回 view，invalid/unknown 不再变成 `{}`。
- 缺 key 时：
  - `EXISTS` 仍是 FALSE；
  - `NOT_EXISTS` 仍是 TRUE；
  - `EQ / NE / TRUTHY / FALSY / IN / NOT_IN` 返回 UNKNOWN，理由
    `missing-key`。
- `decoded` 下值为 `None` 与 key 缺失仍然分开：
  - `{"uid": None}` 的 `EXISTS` 是 TRUE，`EQ None` 是 TRUE；
  - `{}` 的 `EXISTS` 是 FALSE，`EQ None` 是 UNKNOWN。
- 空条件组返回 UNKNOWN，不能生成 witness。
- invalid/unknown 不能升级为 `RUNTIME_VERIFIED`。
- 搜索目标到了但条件没验证时，状态是 `TARGET_REACHED_UNVERIFIED` 或
  `PROXY_PROGRESS`，不是 `VERIFIED`。

### 测试矩阵

新增并更新：

| 输入 | 条件 | 结果 |
|---|---|---|
| decoded `uid=7` | `EXISTS` / `TRUTHY` / `EQ 7` | VERIFIED_TRUE |
| decoded `uid=None` | `EXISTS` / `EQ None` | VERIFIED_TRUE |
| decoded `{}` | `EXISTS` | VERIFIED_FALSE |
| decoded `{}` | `NOT_EXISTS` | VERIFIED_TRUE |
| decoded `{}` | `EQ None` | UNKNOWN |
| absent | `EXISTS` | VERIFIED_FALSE |
| absent | `NOT_EXISTS` | VERIFIED_TRUE |
| absent | `TRUTHY` / `EQ None` | UNKNOWN |
| invalid / unknown | 任意 | UNKNOWN，无 witness |
| 空条件组 | — | UNKNOWN，无 witness |
| 不同 client | 同一条件 | 各自判断，不合并 |

结果：Session 相关 `87 passed`。

## SS-05C：检查点必须是“准备前缀”，不是整条成功链

### 问题

旧 `checkpoint_from_guided_result()` 默认 `prefix_len = len(steps)`。
它保存的是“完整成功序列可重放”，不是“状态准备前缀可复用”。

旧重放把 prefix + suffix 作为一个 Trace 窗口求并集，所以
`suffix_target_covered` 可能把前缀已经覆盖的目标算进后缀。
`replay_success` 也主要看前缀是否覆盖目标，容易把两种成功混在一起。

### 改法

新增两个概念：

- **Target Witness**：完整序列到达目标，冷启动重放仍到达；
- **State Preparation Prefix**：严格短于完整序列的前缀，在不执行目标后缀
  的情况下建立 Session 条件。

新增 `find_verified_preparation_prefix()`：

- 只检查 `k < len(steps)` 的前缀；
- 每个候选都从新 reset 的客户端独立执行；
- 前缀自己已经覆盖目标时跳过；
- 找不到严格更短的前缀时返回 `NO_REUSABLE_PREFIX`；
- 没有 reset hook 时返回 `UNVERIFIABLE`；
- 选择“最早的 step 边界”，不宣称全局最短子序列。

检查点新增元数据：

- `checkpoint_kind`：`target_witness` / `state_preparation`
- `baseline_id`
- `client_scope`
- `condition_group_id`
- `source_sequence_hash`
- `validation_observation_point`
- `verified_condition_witness`

旧 v1 文件缺少这些字段时用安全默认值，不把默认值当成已验证事实。

重放结果拆成：

- `preparation_verified`
- `target_witness_replayed`
- `prefix_target_covered`
- `suffix_target_covered`
- `suffix_incremental_blocks`
- `whole_sequence_target_covered`

准备前缀重放的状态是 `PREPARATION_VERIFIED`，不是 `REPLAY_VERIFIED`。
`REPLAY_VERIFIED` 只给 target witness。

后缀 Trace 分段：

- 先单独跑前缀，验证准备条件；
- 再冷启动跑 prefix + suffix，在前缀结束处切分 Trace；
- 后缀目标覆盖只看 suffix span；
- 后缀可能 `clear()`，所以条件观测点放在后缀执行前，不能靠终态反推。

### 反例

- `[POST /authenticate, GET /protected]` 的准备前缀只能是一步 POST；
- 前缀后又 `logout`，后缀 `/protected` 不能借用历史登录事实；
- `/protected` 与 `/protected_truthy` 两个后缀各自 reset + 重放前缀；
- 后缀只跑 `/noise` 时 `suffix_target_covered=False`；
- 没有 reset / client scope 不匹配时 `UNKNOWN`；
- target witness 的 suffix 仍单独计量，不把前缀覆盖算成后缀覆盖。

结果：`100 passed`（Session 相关 + 架构边界）。

## 还没做到

- 只支持 Flask 默认签名 Cookie Session。
- 没有实现显式 `session.get("uid", default)` 的默认值表达式解析；因此
  缺 key 的 `EQ / TRUTHY` 目前是 UNKNOWN，而不是猜测。
- 跨函数读取仍可能标 PARTIAL/UNKNOWN；T2 变体只验证了“写辅助函数 +
  目标函数读取”的场景。
- 准备前缀每次复用仍要重新执行前缀；这不是物理快照，成本不能写成 0。
